# 核心能力验收：单轮闭环与连续闭环

2026-11-12与用户明确对齐的验收标准。本文定义如何验收，不表示目前已经通过。完整工程回归、真实运行验收与研究判断质量分别报告。

## 两个层面

| 层面 | 要回答的问题 | 通过条件 |
| --- | --- | --- |
| 单轮闭环 | 初始方案确认后，系统能否自动把一次训练做完并拿回可信结果？ | IterLab自行准备工作包、提交LPAI组件库或开发空间任务、保存原身份、后台监控、回收并核验实际训练结果，无外部开发助手代提交或代回收 |
| 连续闭环 | 拿到结果后，系统能否自己决定并执行下一步？ | 结果事件自动接续原会话，模型读取真实结果、分析并提出有依据的下一实验或方案修订，经内部审议与原授权校验后再次提交、监控、回收，并完成比较和轮次评审 |

连续验收以三轮实际有效训练为目标，观察两次结果驱动的接续；最低应有两轮实际有效训练及一次完整接续。报告必须写明完成的是两轮还是三轮、完成几次接续，不能用“三次提交”代替“三轮有效训练”。只完成单轮不能宣称连续闭环通过。

## 场景准备与首次确认

选一个数据和代码来源清楚、训练耗时短的小任务。明确初始方案、选定的执行方式（组件库或开发空间）、资源/镜像/数据/输出位置、主指标、固定评价协议、资源上限及本次停止条件。先确认所选资源实际可用，不为验收擅自增卡或更换平台。

用户只需对初始方案及基本资源约束做一次确认。授权内的普通实验调整与方案修订由IterLab自行分析、审议和执行；不逐轮要求人类批准。首次申请或增加GPU数量、超出既定资源/数据/执行边界、企业强制审批及用户明确暂停仍按原规则处理，不能为了演示绕过。

小型任务可使用CPU组件库来验证实网链路；这不等于GPU训练或深度学习已验收。若要声称GPU能力通过，必须实际使用已批准GPU并取得训练证据。开发空间与组件库分开记录，验证其中一种不代表另一种也通过；选定远端后不能本地代跑。

## 层面一：单轮闭环

初始方案确认后，由IterLab自身依次完成：

1. 核对并冻结方案、数据/源码/配置及输出合同，完成所选平台的提交前检查。
2. 按方案创建或复用组件并提交任务，或通过已验证SSH在指定开发空间启动实际训练；保存组件/空间、任务及本地运行的对应身份。
3. 用轻量后台监控排队、运行和终态，不让模型持续轮询，不依赖用户保持浏览器打开或发送“继续”。
4. 终态先回收声明的指标、预测/日志等必要产物到本地，校验任务归属、输入身份、文件摘要与结果完整性；大权重可明确保留远端索引。
5. 能从实际产物复核指标，形成可供原会话分析的结果事件。平台成功、产物就绪和目标达成分别判断。

没有真正训练、只有零拟合探针、Pod启动、空输出或缺损指标时，不算单轮有效训练通过。故障处理能力可以单独通过，但不能代替有效结果链路。提交结果未知时先对账原请求，禁止用新任务掩盖或重放。

## 层面二：连续闭环

在层面一的基础上，继续观察：

1. 结果回收后，后台向原会话投递一次接续事件，原生Codex读取已保存结果，无需开发助手代发提示。
2. 模型解释关键结果及问题，区分工程失败、证据不足和算法表现；提出与观察相关、可检验且成本合理的下一步。
3. 方案内实验可保持总体模型、调整一个有依据的因素；只有证据需要时才修订上层路线，不为凑覆盖强行换模型或发布大版本。
4. 下一候选经过产品内的Critic/具体版本审议、授权与资源守卫，原累计不重置；由IterLab实际再次提交、监控和回收。
5. 后继结果与已有对照公平比较。记录原判断被支持、削弱还是仍无法区分，形成评审和下一方案或结束建议。

目标三轮训练不代表每轮都必须发新方案。两次有效接续可以分别体现方案内实验迭代或有证据的方案修订；若只观察到其中一种，报告只能声明这一种，不能扩展成“大方案自动迭代已通过”。因证据充分而提前达标/合理收束可作为独立观察，但未跑足轮次就不能声称完成三轮连续验收。

## 指标目标：越高越好，但不要求逐轮涨分

可把macro-F1、准确率等设为最大化目标，预先确定一个主指标，并冻结数据划分、标签、预处理边界和评价方法。延迟、显存或类别召回等可作为附加约束。不能在分数不理想后换口径、读测试标签调参或只展示最好的一次。

同一个验证集多次选择候选属于探索性比较；没有独立测试或其他充分验证时不宣称泛化提升。小样本涨分与单次随机波动需说明限制，不直接声称统计显著。

验收不以“每轮上涨”为必要条件。负结果也有信息价值：模型应据此缩小解释范围、保留较好对照、停止已否定方向或设计区分解释的最小下一步。无依据调参、机械换模型、忽略反例、重复已否定方向或不公平比较，应记为研究判断问题，即使分数偶然上涨。

## 工程失败与有效轮次

同一实验的初始化失败、入口修复、配置修正和重跑归入该实验的运行尝试，保留每次UID、失败原因、改动和产物。不能把修复重投计为新科学方案，也不能以三次初始化失败宣称三轮研究完成。

失败后能够有据修复并最终运行是能力的一部分；无证据原样重复、重复提交未知任务、放松门禁或更换身份不算修复。达到本次资源/重试边界时保全证据并说明阻塞。

## 人工介入的标注

初始需求答复、初始方案确认和预先授权的资源范围属于正常用户参与。其后若开发助手代发“继续”、指定下一实验、补写关键结果、代操作SDK/网页提交或代回收，必须单独记录起因、动作及影响；受影响段落标为人工辅助，不能算IterLab自主通过。

脚本调用正式接口、模拟平台响应、合成指标和离线Demo可以验证各自工程范围，不能代替真实宿主自动链路。单独直接调用模型给建议也不证明角色交接/后台自动接续。验收操作者不得把自己的决定伪装成模型自主选择或用户点击。

## 停止与报告

本次验收预先约定短时间窗、目标轮次、单次时限和资源上限。这是验收边界，不改产品日常默认；结束不追加任务凑成功。遇用户停止、资源越界、未知请求或证据损坏先保全状态。停止模型推进不自动取消已提交云任务。

最终报告至少给出：

- **单轮闭环结论**：通过/部分通过/未通过/未测试，实际平台、任务身份、训练及回收证据。
- **连续闭环结论**：同样独立判定，实际有效轮数、成功接续次数，以及是否有外部操作者驱动。
- **研究判断结论**：逐次说明结果、关键假设、选择理由、后继执行及负结果如何改变判断。
- **指标结论**：固定口径下的真实数值及比较限制，与功能是否跑通分开。
- **人工介入、消耗与缺口**：额外提示/审批/修复、实际任务及模型轮次、停止原因、未覆盖平台和场景。原生turn数不冒充模型API调用次数。

失败和部分通过也应形成演示与可复核报告，不能为了好看补造结果。完成某个小任务不表示所有复杂研究、GPU、多卡、长排队和服务重启组合均已验收。
