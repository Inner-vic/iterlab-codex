# SDM 思想承接：基础实现与 Demo

基准为用户指定 BMAD ML 仓库的原始提交 `ec870b0e12b0932741a193520a004cba5ae9f3c3`，其中 SDM 是21步研究生命周期。承接清单见 [sdm-inheritance.json](../methods/research/sdm-inheritance.json)，每项列明原则、现有实现及部分承接边界。它不是要求每次研究执行21步，也不是后续34项职责归并为26项的覆盖证明。

本次定位是基础 Demo：把必要思想接入现有记录、评价、运行和展示，不另建生命周期、模型循环、签名服务或 HPO 平台。代码可提供相应机制，不代表已经证明 Agent 会在所有真实研究中正确使用。

## 已复用的能力

| SDM 设计 | IterLab 承载 | 边界 |
|---|---|---|
| 需求与研究问题 | 项目、alignment/question/plan、问题核查 | 保存来源不证明假设有价值 |
| 实验协议与输入冻结 | evaluation_contract、不可变方案、研究授权、输入快照 | 不认证所有数据/模型语义 |
| 工程实现和就绪 | Codex工具、受控diagnostic/evaluation、数据/设计/工程方法 | 语法检查不是模型或独立代码审查 |
| 运行、失败与证据 | Run/Attempt、LPAI身份、回收、完整索引 | 平台成功、产物就绪与研究成功分开 |
| 审查与后继 | Critic、inquiry_outcomes、轮次评审、方案版本、研究脉络、续接 | 同线程角色不是隔离盲审；不能保证下一方案有效 |

## 新补的基础机制

### 基线选择与更新

复用 `research_record`，不创建平行基线注册平台。普通候选保持研究/结果记录，只有明确选择时填写 `baseline_selection`：适用目标、候选原记录、候选名称、身份文件、原选择、理由及对旧比较的影响。原记录与所引用文件必须真实存在并保持同项目身份。

同一适用目标的更新需引用当前选择，避免用过时状态覆盖；旧选择和引用不改写。方案/实验通过 `baseline_ref` 明确使用哪一次选择，后续换基线不改变已有比较。加载权重、给目录取名baseline、首次跑通或单次涨分都不会自动确立基线。这不等价于原版完整B01—B04复现、弃用与依赖治理。

### 探索与确认

现有design方法已区分探索和确认，本次将必要关联落实到 `confirmation_plan`。先保存引用完整选择依据的决策，再在事前方案中固定搜索比较、所选候选文件和确认理由。

基础程序核对相同数据/评价协议、候选与数值规则，以及未用于选择的新pair。选择记录保留相关实际尝试索引，包含失败/取消；这不是要求模型逐个读取全部结果。确认结果还需来自该事前方案的实际快照，候选的指标产物与运行不能复用搜索身份。比较报告区分候选产物与纯参考产物，已有对照不被误当成必须重新训练的候选。

当前只实现同协议新pair轴，不提供完整HPO搜索执行器、受保护测试环境或独立数据集确认。新seed/fold标签、相同文件身份和程序检查均不证明统计独立、功效充分或训练代码真正消费了声明语义。旧比较报告仍可读取；确认所需的新来源标识通过重做原归档核验取得，不要求重训或覆盖旧报告。

### 四态结论与执行收束

`scientific_assessment` 支持两类依据：

- `comparison_rules`：由程序读取原数值核验报告，按固定条件产生支持、反对、证据不足或比较无效。不能传入预期outcome。判断对象限定为“候选是否满足冻结的数值条件”，不是自动证明研究机制或模型普遍有效；失败条件也不等于模型路线无效。
- `evidence_review`：有实际文件依据的研究判断，保留理由和局限；支持/反对不可无证据，也不能用此途径自报确认性数值通过。

已有问题层 `inquiry_outcomes` 继续保留，统一显示词汇，不另建问题生命周期。结论修订通过 `supersedes` 关联同一问题并追加记录，图谱显示修订关系。`stop_reason` 继续表示执行收束原因；预算结束不自动生成反对或支持。

### 按需审查和就绪

`study_review` 复用现有原文摘录、文件身份和原生命令收据检查。可分别记录planning/protocol/implementation，以及领域语义、泄漏、基线公平性、统计有效性、部署一致性五个视角。

只填写适用部分；checked必须有真实核查依据，not_applicable需要理由，未记录表示未知。已明确声明的必要前提仍缺证据时拦截正式fit；授权内diagnostic/evaluation可以用于补证，避免把解决前提所需的检查也挡住。不强制所有项目绑定坐标单位、不要求每轮做完整五视角报告，也不把原文核对当成实际模型测试。

### 结果分析只作小幅状态筛选

保留全部尝试不等于每次分析全部结果。`research_status` 简报复用现有运行与回收状态，给出有界的待处理索引：

| 已有状态/证据 | 日常分析材料 |
|---|---|
| 新的可用模型结果 | 指标、产物入口，按当前问题读取 |
| 失败且有诊断材料 | 失败诊断入口，不作性能结论 |
| 未知或缺少证据 | 待核对身份/缺口摘要 |
| 运行中、无结果取消、已有分析记录且证据未变 | 收起正文，保留状态计数和完整索引入口 |

这是只读选择视图，不是新增状态机或分析流程。已有分析记录不认证其正确；状态或证据身份变化会重新进入待处理。`view=full` 保留原分页清单，轮次收尾的完整引用检查继续防止遗漏失败和负结果。正常分析不要求逐个分析全部尝试或重复加载日志。

## 如何融入工作台

- 原有 `research_record` 增加可选字段；不会要求普通研究填写完整SDM表单。
- `research_status.study_integrity` 返回有界的当前基线、近期科学判断和可信范围；详细证据通过原 `research_snapshot` 读取。
- 记录详情显示基线选择、确认约定、数值判断范围、适用检查和停止原因；图谱保留原记录，增加显式基线更新/结论修订引用。
- 新能力和检查引擎随方法快照固定。旧项目不自动升级，不静默改写旧方案或结论；已有项目使用新字段前需空闲时显式升级。活动线程不热换规则。
- 独立签名、可信根和外部账本未实现。程序明确显示本地留痕与审议的边界，不能据Critic角色或本地哈希声称不可抵赖认证。

## Demo 与验证

从仓库根目录，用 `scripts/run-quiet.ps1` 前台运行真实Python可执行文件，参数为 `scripts/study_demo.py`。默认输出 `.evidence/sdm-inheritance-20261110/demo/preview.html`，重复生成时用新的 `--out` 路径，避免覆盖已有示例。

Demo复用真实研究API、冻结和归档链路，执行三次微型静态指标评估，展示四态、基线更新和停止原因分离。数据全部合成，零模型训练、推理和企业调用；隔离数据目录与主服务无关。离线HTML复用工作台实际组件及详情数据，不需要持续运行服务。`--serve` 仅为开发者提供只读预览，不启动Kernel。

程序回归覆盖身份、选择、确认、规则、缺证据、状态筛选和原记录保持。开发者另外对本机已有材料做有界只读回放，核对原归档及合同，保留“未满足条件”和“材料不可比”的区别，不创建新训练或新基线；没有完整生产数据库副本。个人项目身份与回放收据不随共享源码发布。

这些证据验证基础机制，不证明Agent自主采用质量、统计可靠性、重大改向收益或RoadModel完整训练闭环。后续按真实问题逐步强化，不因Demo可运行就宣称全面替代原版科学治理。
