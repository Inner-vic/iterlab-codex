# 五阶段／34项职责向26项研究能力整合方案

原设计日期：2026-10-28。本文保留34项向26项归并的理由和兼容要求，不是最新运行状态清单。当前承载见[能力实现](capability-implementation.md)，实网范围见[核心交接](core-handover.md)。早期逐版人审已扩展为显式自主策略，经Critic及原授权校验继续；手动策略保留。合并须有理由，不能为数量目标删除职责。

范围仅为独立项目iterlab-codex。原SDM及8769保持独立。原34项主归属及8组合并理由保留在下表，方法/源码对照见[内置研究模块](builtin-research-modules.md)；未迁入旧设计不作为已有能力。

## 设计结论

建议保留五阶段，将34项职责整理为26项逻辑能力，做8组有明确边界的合并，暂不直接删除研究能力。这一数量来自职责归并，而非为了达到指标拆分或删减。

四种对象必须区分：

1. 五阶段：当前研究焦点，可前后往返，不是有向无环的必经流程。
2. 26项能力：按条件使用的研究职责，既含方法也含程序保障，不是每轮要执行的清单。
3. 工具接口：服务于能力的一小组真实操作；不为每个能力建立一个工具，也不因改编号重写Codex循环。
4. 探索图节点：真实共识、具体方案、重要实验、结果和改向。数量由研究过程决定，不固定为26或34；普通工具调用留在执行活动中。

Codex继续负责研究判断、方法选择和工具循环，工作台管理可靠业务状态。语义压缩、原生消息/工具执行等已有内核能力不另包装成研究步骤。需要补证时先用现有产物；新训练只有在确有信息价值和有效授权时启动。

架构选择及实际默认：Codex内核＋研究级状态/事件编排＋内置能力，原生SDM Skill作为可选参考和旧项目兼容。确定性子链程序执行，研究路径根据证据选择；不建设固定26步流水线或第二个LLM循环。新项目已不强制绑定Skill；原FordA项目已按用户授权显式迁移并保留旧快照。具体取舍见[研究编排架构决定](research-orchestration-decision.md)，各能力实际承载、触发和缺口见[26项实现对照](capability-implementation.md)。LPAI组件提交、SSH传输和产物回收已有适配代码，不能再按早期状态称为“未迁入”；但最新小型LPAI完整闭环未通过，代码与实网结论须分开，见[参考范围](preservation-status.md)。

轮次定义：一个获批方案内可开展多次实验；收尾是本轮评审及具体下一方案或有依据的结束建议。早期“下一方案一律人审”仅对应manual策略；当前autonomous策略允许原授权范围内经Critic审议及程序校验采纳后继，首次GPU或扩大资源等越界仍确认。该规则是实现合同，不是连续自主研究已验收的证明。

## 实现载体不限定为Skill

用户进一步明确：LPAI等能力适合做成系统固有功能，不应每次读Skill才知道如何执行。对此采用“运行能力代码化、研究方法按需指导”的分工。SDK/CLI是外部官方依赖，适配器是本项目程序，Tool是Codex调用接口，Skill是方法说明，四者不是同一个概念。

| 归属 | 具体内容 | 调用和维护方式 |
|---|---|---|
| Codex内核 | 文件/命令、原生对话、引导/中断、安全审批、语义压缩 | 复用原生机制；不再用SDM重写一套循环 |
| IterLab研究核心 | 共识/方案/实验/运行/产物身份、审核、累计范围、证据索引、状态投影、持久事件续接 | 程序/API及数据库维护；用户页面和Codex工具使用同一业务实现 |
| 执行与平台适配 | 本地、SSH、LPAI，及Git/GitLab官方接口 | 通用运行管理内置，平台以可启用适配器接入；配置后直接提供结构化操作，不让模型临场猜SDK参数或读Skill拼命令 |
| 研究方法 | 如何立假设、选对照、解释反例、设计有信息量实验及必要改向 | 可用原生SDM Skill、按需参考及少量会话指导；不把经验口诀硬编码成自动改参 |

“固有能力”指接口和生命周期由系统实现，不等于将公司专属依赖硬编码为所有项目的启动前提。未配置LPAI时仍可使用明确授权的本地或SSH；启用且绑定LPAI后遵循其执行策略，不因缺少训练传输而静默回落。

### LPAI现状与目标

已核对当前代码：`lab/company.py`已经实现官方lpai-agent适配、连接/项目绑定、操作身份/审批、持久watch与低频后台查询；`lab/kernel.py`直接注册company_context、lpai_read及company_action。它们不是通过加载LPAI Skill来执行。现有实现仍只覆盖资源/任务读取、受审批的已绑定空间启动、已有任务观察和终态分析投递；真实训练提交、代码/数据同步、loss/指标、checkpoint/产物回收没有因此完成。

后续正常调用路径：Codex选择研究动作→结构化工具→IterLab运行服务→官方LPAI适配→持久任务/产物→后台事件→原会话结果分析。页面直接调用同一服务；后台状态查询不占用模型turn，不把每次轮询写入模型上下文。完成后是否分析、继续训练以及执行范围仍由真实授权和证据决定。

下午整合应优先：

1. 能力目录标明实际承载者、可用操作和实现状态，不把“Skill里写了”当作程序已支持。
2. 由服务检查配置、官方依赖和真实连接状态；已确认的状态按版本复用，必要时刷新。暴露可用操作，未实现操作明确缺失，不让模型反复查文档试错。
3. 技术接口字段、路径、任务ID、重试/幂等、超时、进程退出及日志索引由程序管理；研究模型只负责有实质判断的部分。NaN/Inf等确定性异常可由程序提示，但不能自动把原因认定为学习率过大。
4. 平台查询/后台监控可在没有读取SDM/LPAI Skill的情况下运行，独立做适配器回归；Skill缺失不能妨碍用户直接查看已绑定任务状态。研究模型所需的方案方法绑定规则另行保留。
5. 所有工具目录/能力升级保持已有thread、待审批请求与历史调用兼容；不在活动轮次改变其接口语义。

此次新增的是明确承载方式和整理既有平台能力，不扩大下午云端操作授权。完整LPAI训练链路仍是后续独立工作，不把架构调整称作已完成实网训练验收。

## 8组合并的具体理由与保留条件

| 合并 | 充分理由 | 必须保留的差异／验收 |
|---|---|---|
| 1＋22 → C01 | 都维护同一研究任务的目标、已知信息和需求变更；分开容易登记表与共识内容不一致 | 登记身份仍稳定；后续共识修订不覆盖原用户意图，记录谁/为何修改 |
| 4＋5 → C04 | 选基准首先要判断已有证据是否可信、是否需要复现；不应默认“先选再强制重跑” | 声称复现必须有实际运行；加载checkpoint、引用历史和新复现的证据等级不能混同 |
| 7＋26 → C11 | 环境准备与资源发现共同回答“在哪、用什么条件能执行”；当前Codex工具可直接发现并检查 | 账号可见、实例绑定、依赖可用、真实训练成功是四件事；禁静默回落本地 |
| 9＋10 → C12 | 实现范围是本次代码变更的边界，不需要独立规划轮次再重复描述实现 | 修改须与方案对应；大范围改动与目标变更需要相应评审，不能以写成代码替代符合协议 |
| 11＋12 → C13 | 风险代码审阅和接口/数据实际验证都支撑工程可信性，归入一个能力可避免重复“检查完成”节点 | 静态评审、语法检查、实际运行检查各有结果；一项通过不能覆盖其余失败，独立评审身份不删除 |
| 18＋29 → C21 | 评审上下文应是同一证据库的按需视图，不应另建模型维护的平行“证据包” | 原始日志/权重/尝试留存；摘要和索引可重建，关键证据可按需取回，不把压缩当删除 |
| 20＋32 → C23 | 结论、建议及其充分性必须一起说明，否则易先下结论后补理由 | 观察与推断、支持与反证、未知与限制分开；提建议不等于准予执行，自评不等于独立审查 |
| 31＋34 → C08 | 多轮评审问题就是方案修订的输入，分成平行台账易重复提问、丢退回理由 | 保留每个问题的证据、答复和处置；新版本批准独立存在，不能把批评者变成自批者 |

这些主要是能力归属及数据视图归并。不能仅因目录合并就删除独立运行收据、审批记录、校验器或原始证据，也不据此强制把所有表/代码塞进同一个模块。

## 移出独立研究步骤、暂不迁入或保留的内容

本轮不建议直接删除34项中的任何研究能力。以下只可在核对实际代码后移除重复实现／不适配包装：

- 自建LLM执行循环、整段会话手工拼接、机械顺序调度：与Codex内核职责重叠，当前新项目已明确不采用。若发现残留调用，记录入口/证据后停用并归档；原项目与源SDM不删除。
- 把“生成评审上下文包”作为独立研究轮次：由C21从持久证据索引按需取视图；保留源证据和必要摘要，不让模型反复维护第二份事实。
- 每次工具后都调用阶段/状态工具、把读文件/修错自动画成研究分支：确定性状态由原事件投影，只有语义焦点变化和重要研究决定需要留节点；不删除原始活动。
- 同一原生约束在宿主长提示词、Skill入口、多个参考中重复全文：约束实现保留单一权威来源，方法入口只引到必要参考；不能只为减少字数删掉边界。
- 原SDM签名、可信根、外部账本锚定和独立认证协调器：尚未迁入，不强行复制。保留原件/来源及未实现说明；不把“没迁入”写成“已删除一个可用功能”。

明确保留为独立检查：C14授权、C15预检、C16输入身份、C22可复核性、C24研究决策、C25资源释放。它们对象、失败后果和事实依据不同，不能以“一键检查”掩盖。

真正删除前必须有：旧入口/用途、重复或不适配的证据、替代落点、行为保持与回归证据、历史兼容及回退路径。缺一则先保留或标记deprecated，不做硬删。不批量删除表、历史文件、审核记录或云资源。

## 2026-10-28原始适配计划（历史设计依据）

1. **统一能力目录**：独立可校验目录维护C01—C26、旧编号、触发条件、方法引用、实际约束/工具、输出与实现状态。目录用于代码/文档一致性，不整体塞入每个原生turn，不生成26个新工具。
2. **研究入口去重**：在现有research_status上提供有界研究简报，按需包含共识、当前确切方案、审核/运行与最近关键节点；research_snapshot共用底层读模型并保持兼容，避免同一事实拼接两套逻辑。常规工具调用后不重复全量读取。
3. **版本化方法更新**：原项目固定的Skill摘要不能直接覆盖。新增显式、空闲时升级及旧/新摘要和理由记录；旧投递/旧研究记录仍引用旧方法，历史文件不重写。先做隔离迁移测试，再决定是否升级真实项目。
4. **历史正文与当前状态分开**：原计划/实验提案正文永远保持原字节；审核和运行状态来自事件/收据。旧记录中“尚未训练”属于形成时事实，界面须说明历史时间与当前可核实状态。不能把“最近一个方案/结果”随便当当前进程。
5. **精确实验关联**：需要时给运行绑定明确trial/plan来源并检查项目归属；旧运行缺少映射就显示未知，不凭顺序猜测或制造因果。只有确有证据才能补充派生关联，不更改原收据。
