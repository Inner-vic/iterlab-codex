# 本地存储与备份

IterLab使用本地SQLite保存项目、会话、方案、运行身份和证据索引，工作区中的数据、报告、预测与模型文件独立存储。Codex/EPT的原生线程和登录资料仍由各自官方工具管理，不随IterLab备份复制。

## 存储分工

| 位置 | 用途 | 保留方式 |
| --- | --- | --- |
| `.data/workbench.sqlite3`及其WAL | 正式项目、会话、研究记录、提交与接续身份 | 不按磁盘预算删除记录，不手动删除WAL |
| `.data/workspaces/`、`.data/records/` | 研究文件、数据、结果和证据 | 保留原件；大权重另按项目管理，不为界面测试整份复制 |
| `.data/backups/snapshots/` | 新的压缩数据库/配置备份 | 相同内容复用已核验备份，默认目录预算2GiB，可显式调整 |
| `.evidence/` | 开发验收报告、截图、运行收据 | 保留结论和必要证据，过期全库副本按恢复点策略清理 |
| `.evidence/tests/<UUID>/` | 自动化测试临时夹具 | 测试应自行关闭连接并清理；已确认不再使用的旧夹具可删除 |
| `.runtime/` | 可复用的已安装运行依赖 | 不视为研究记录；清理前确认可重建，不与数据混放 |

SQLite用于当前每人本机独立工作台，无需另外部署数据库服务。大量空间消耗来自工作区产物、重复备份和测试副本，换数据库不能解决复制策略。正式事件表也会增长；冷存档必须可追溯，不能直接截断接续所需事件。

## 归档、删除和磁盘空间

归档保留记录；移入回收站可恢复；永久删除按明确确认事务删除该对象的本地数据库记录和关联索引。删除入口可直接选永久删除，不要求先归档。详情见[会话管理](session-recovery-and-skills.md)。这属于用户主动删除，不是按容量静默删历史。

永久删除不清除工作区文件、Codex原生历史、已有备份或LPAI资源，也不保证SQLite文件立即缩小或磁盘安全擦除。清理磁盘须另外核对具体文件、正在使用的运行和备份；不能把“数据库记录已删除”当作“整份项目已从磁盘擦除”。

## 标准备份入口

从项目目录执行，使用已配置的Python解释器；Windows按AGENTS.md经`run-quiet.ps1`前台运行。

```text
python scripts/storage.py snapshot
python scripts/storage.py snapshot --max-backup-gib 4
python scripts/storage.py snapshot --data-root D:/IterLabData --destination E:/IterLabBackups
```

工具先通过SQLite在线备份API创建一致快照，可包含已提交的WAL数据；临时未压缩副本放系统临时目录，不在研究盘再留一份全库。归档中保存SQLite、IterLab设置、逐文件SHA-256和表行数。压缩后重新读取并校验，成功才发布最终ZIP；失败只清理本次未发布的临时文件，不删除正式库或旧备份。

相同数据库与设置会复用校验通过的已有归档。默认2GiB是**备份目录的存储预算**，不是训练/拟合次数或研究预算；达到后拒绝继续制造副本，提示整理或换备份位置，正式研究记录不受删减。它不是自动轮转删除授权，也没有设置额外定时任务。

`scripts/snapshot.py`使用同一压缩实现，但为部署用途保留活动/未知原生轮次与本地计算拦截。备份成功不等于可以停止服务；部署前还需单独核对任务状态和原身份。

## 核验与恢复

```text
python scripts/storage.py verify --archive D:/IterLabData/backups/snapshots/workbench-....zip
python scripts/storage.py restore --archive D:/IterLabData/backups/snapshots/workbench-....zip --destination E:/IterLabRestore
```

恢复目标必须是一个不存在的新目录，不允许覆盖运行中的`.data`。恢复会核对归档成员、SHA-256、SQLite完整性和全部表行数。若进程异常遗留`snapshot.lock`，先核对原PID和备份状态，不盲删锁或重放未知操作。

**数据库备份不是整台电脑或完整项目文件备份。** 工作区数据、权重与报告不在这个小型归档里，换电脑/整盘恢复时应另备份对应工作区目录，并保留路径关系。CLI登录和SSH私钥不随项目分发。

## 历史副本清理原则

采用明确清单，保留最早可用基线、最近三个恢复点、近七天每天最后一个恢复点，再删除不再需要的旧全库副本。清理前必须有已验证的当前备份并完成恢复测试。只针对标明用途的冷副本，不影响正式数据库、研究文件、原始产物和验收结论。

Windows NTFS可对冷备份做透明压缩，保留原路径和字节；维护工具逐文件验证SHA-256，排除正式库、硬链接/符号链接、未决WAL/日志、近期变化和非备份文件。它用于保留的旧恢复点，不意味着所有旧副本都应永久保存。

测试夹具清理限定在本项目`.evidence/tests/`下的UUID目录，先确认无活动测试，排除近期修改、链接和未知用途的内容。不清理其他项目、Codex客户端目录或系统文件。

## 验证范围

存储回归覆盖真实SQLite/设置恢复、WAL提交数据、相同内容去重、容量失败保留原件、拒绝覆盖、损坏归档、路径穿越和恢复点选择。正式库也已进行一次独立临时目录恢复及核心表逐行摘要核对。原研究工作区与外部CLI资料的跨机器完整恢复不在该数据库恢复测试范围。
